## 一、先建立事实基础（按顺序读，别跳）

1. `AGENTS.md` —— 仓库宪法：开发范式、判定方法、反模式清单。**它会告诉你「怎么查状态」而不是「状态是什么」**
2. `.handoff/PROTOCOL.md` —— 接力契约：状态机、回执必填字段、五条红线
3. `.handoff/HANDOFF.md` —— 交接主文档：架构速览、当前能力、本次任务、验收标准
4. `.handoff/docs/` 按 HANDOFF 第 6 节顺序读：架构 → 分支 → 版本 → 构建 → 部署 → 测试 → 待办 → 日志

读完你应该能回答三个问题，答不出来就回去再读：
- 这个项目由哪几块构成，客户端两种游玩形态各自的资源从哪来、存档走哪条链路
- 三个远端分别是什么角色，哪些能推、哪些绝对不能碰
- 当前版本是多少、测试基线是多少项、本次任务的验收标准有哪几条

## 二、开工前的三道门（都必须过）

```bash
bash tools/handoff.sh status     # 看当前任务、版本、状态
bash tools/handoff.sh verify     # 交接包完整性，必须 0 失败
flutter analyze                  # 必须 No issues found!
```

任何一道门没过，先修它或提出问题，**不要开始改业务代码**。地基坏的时候，后面的判断全是错的。

## 三、认领任务（语义回读，不是「收到」）

把 `.handoff/state.json` 的 `task.status` 从 `dispatched` 改为 `accepted`，并在 `receipts[]` 追加第一条回执，
其中 `readBack` 必须写出你**实际读到的**三件事：

- `taskTitle`：本次任务标题
- `versionBefore`：当前版本号（从 `pubspec.yaml` 与 `state.json.release` 交叉读到的一致值）
- `testsBaseline`：测试基线（总项数 + 服务端/客户端各多少）

抄错任何一个，视同未认领，会被打回。然后再把状态推到 `in_progress` 开始工作。

## 四、干活的基本纪律

**改动前**：
- 先看既有的实现与断言。启动/导入/迁移/切换形态的互斥、ZIP 解压、本地资源服务器、在线心跳、
  存档版本语义都已经有实现与测试。**重造一套是这个仓库最常见的破坏方式。**
- 任何破坏性入口（启动游戏、导入资源、切换形态、改存储位置、删除资源）都要检查状态门禁：
  内存门禁 + 持久化事务状态，两者缺一不可。
- 新增文件读写或代理逻辑前，先对照已修过的安全坑：路径穿越、符号链接逃逸、压缩包条目越界、鉴权头伪造。

**改动时**：
- 断言加进现有套件（客户端 `tool/check_*.dart`、服务端 `tools/test-*.sh`），不新建框架。
  本仓库的 Flutter widget/单元测试套件是**有意移除**的，不要重建 `test/`。
- 测试基线只许上升不许下降。
- 安全相关的修复必须同时给正例与反例。
- 性能敏感路径要有资源占用判据，不能只证明「跑通」。

**红线的红线**：
- 个人服务器地址、令牌、密码**绝不写进任何受版本控制的文件**。只用环境变量 / CI secret /
  本地 `.env.local`（600 权限、已忽略）。提交前自查：源码里搜不到域名才算过。
- 上游主线远端**只读**：不推、不改、不提 PR。
- 运维副作用动作（容器重建、网关规则、资源包重打包、建 Release、重启宿主）**不要自己做**，
  写进回执的 `needsHermes` 交回。跨机器构建看清边界：Windows 可执行文件只能在 Windows 机器上构建。
- 安卓真机测试由用户执行。你的职责是给出「点哪几步、看什么、失败抓什么日志」的清单，
  以及按回传日志定位并修代码。

## 五、收尾（交付物只有一种形态：可复核的证据）

1. 修完自测：`flutter analyze` 干净，受影响套件全绿，给出**真实**数字
2. 把 `task.status` 置 `review`，写完整回执（`PROTOCOL.md` 第 3 节字段）：
   `changed` / `commands`（真实命令与输出片段）/ `tests`（各套件真实数字）/ `artifacts`（路径+字节+sha256）/
   `remaining` / `needsHermes`
3. 同一份回执追加到 `.handoff/docs/08-handoff-log.md`（人读版）
4. 新发现的缺陷先进 `.handoff/docs/07-backlog.md`，再决定修不修
5. 跑 `bash tools/handoff.sh verify` 到 0 失败，把输出原样贴进回执
6. 提交：`Type: 一句话` 风格，推公开 fork 的工作分支与私有仓（命令见 `docs/02-branches.md`）

**不许写「应该通过」「预计没问题」「大概是这个原因」**。没跑就写 `not-run` 并说明原因——
回执是自报，接受方会重跑测试、实测哈希、比对 diff。写得圆但经不起复核，比老实说没做更糟。

## 六、卡住的时候

- 现象奇怪先怀疑工具而不是产品：测试出现 `501`/`000` 多半是脚本自己的 URL 拼装问题；
  Windows 构建报 `MSB3073` 多半是 `build/` 与 `.dart_tool/` 状态不一致；PowerShell 语法错误多半是编码。
  这些都有记录，见 `docs/04-build.md` 与 `docs/06-testing.md`。
- 真卡住就把 `task.status` 置 `blocked`，回执写清：卡在哪、已试过什么、需要谁做什么。
  停下来问，比猜着做然后返工便宜。
